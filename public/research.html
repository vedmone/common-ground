Common Ground turns spoken feedback and shared visual attention into a reversible product change. Its strongest opportunity is the complete review conversation: understand, point back, change, explain, and refine.

Evidence, competitive context, interaction design, and an evaluation plan. Product hypotheses are distinguished from published findings.

The concept already has close relatives. Voice plus browser context, point-and-speak interaction, spatial coding feedback, and separate agent cursors all exist. The credible opportunity is an excellent, continuous experience joining those capabilities. A claim that nobody has built anything similar would be too strong.

What you meant

You want to review a product with an AI the way you would with a colleague on a call. You hover over a button and say, “Isme vibe nahi aa rahi.” The AI sees the reference, points back to the same button, offers an interpretation, and can implement a change. It then shows the result and invites correction while the conversation continues.

The key is reciprocal attention. The user's pointer helps the AI interpret “this”; the AI's own pointer makes its interpretation visible to the user. A transcript preserves words. This interaction also preserves the target, timing, interpretation, and resulting change.

Voice

Natural, interruptible turns. Automatic language detection. No need to compose a polished prompt.

Reference

Hover, selection, page structure and recent attention help resolve what “this” means.

Repair

Point back, clarify once when needed, try a reversible edit, then accept or undo.

Why common ground matters

Clark and Brennan's grounding framework describes communication as a joint process of establishing enough shared understanding for the task. The product implication is to make understanding observable, especially before a costly or ambiguous action.

Gergle, Kraut and Fussell's collaborative-work studies distinguish awareness of task state from conversational grounding. Immediate shared visual information can support both. For this product, a visible preview shows the state; a pointer and clarification show the AI's interpretation.

D'Angelo and Begel's pair-programming study found that shared gaze visualization improved partners' ability to respond to implicit references. That supports testing visible attention cues here. It does not prove that an AI pointer will produce the same results.

Our inference: reducing reference ambiguity and making misunderstandings cheap to repair may matter as much as making generation faster. These studies concern human collaboration and different tasks; Common Ground still needs its own user evaluation.

A natural conversation

You, hovering the hero: “Isme vibe nahi aa rahi.”
Ground, pointing to the hero: “This hero? I’d make it calmer and warmer, with a more personal headline. Shall we try that direction?”
You: “Haan, warmer. But keep the illustration.”
Ground: Makes the change, then points to the headline and color treatment while explaining it.
You: “Keep it. Now this button…”

The sample dialogue illustrates the intended flow, rather than a recorded test result. A clear request such as “make this button green” should be executed without an unnecessary clarification round.

Interaction rules

  • Voice is the main surface. Shared page, AI presence, call controls and brief captions stay visible. The full transcript and keyboard access are secondary.
  • Language follows the speaker. Detect each utterance and preserve code mixing. Switching languages should not require leaving the call or changing a setting.
  • Hover is evidence, not certainty. A locked selection takes precedence. Capture the reference when speech begins and retain recent hover history.
  • Pointing communicates. The AI can confirm a target, offer two plausible scopes, or guide a review of changes. Its pointer should not wander for decoration.
  • Clarify only consequential ambiguity. Offer a concrete design hypothesis. Avoid endless questions after the user has already confirmed the scope.
  • Separate work from completion. Show listening, understanding, working and speaking states. Report a successful change only after a valid result exists.
  • Correction remains easy. A version checkpoint, real diff, and reliable undo keep experimentation comfortable.

Why this could become a strong product

The strongest initial user is a founder, designer, or product lead reviewing a running web interface with a coding agent. They already know what feels wrong but may not know the component name, CSS property, or exact prompt. The room can shorten the distance between noticing a problem and assessing a real alternative.

The advantage to pursue is less coordination effort per accepted change. A live voice room could preserve conversational momentum; shared references could prevent wrong-target edits; reciprocal pointing could reveal an error before it becomes code. Reversible changes could help users discover their preferences through examples.

This is also a plausible broader interaction pattern: human and AI maintain shared attention while working in documents, dashboards, design tools, and other applications. That is a product thesis, not a prediction of inevitable adoption. Noise, privacy, social settings, accessibility, latency and user preferences will make voice unsuitable for some sessions, which is why keyboard access remains useful.

The product must earn “best.” A beautiful call screen is insufficient if users wait too long, the AI edits the wrong element, interruptions fail, or undo is unreliable. Optimize successful collaboration rather than the number of animated states or model calls.

What to measure next

Run a counterbalanced pilot with the same ambiguous review tasks in four modes: typed prompts; speech transcription alone; voice with human pointing; and voice with reciprocal AI pointing plus clarification. Use comparable models and editing tools so the interaction is what changes.

Implementation choices and boundaries

The working build uses Sarvam for speech recognition, spoken replies and intent interpretation. Small visual edits can be applied directly to the targeted HTML element; broader preview changes use a coding model. A local companion connects Claude Code to actual project files and takes source checkpoints.

The hosted room edits self-contained preview documents. Existing projects require the companion. Arbitrary authenticated browser tabs, canvas editors, cross-origin frames, general desktop control, and ChatGPT subscription sign-in are not implemented. The current speech pipeline waits for an utterance, transcribes it, interprets it and synthesizes a reply; it is not a continuous native speech-to-speech model.

English and Hinglish speech have passed service round trips. The provider supports additional Indian language locales; those require individual real-user validation before broad quality claims. Source changes in an existing repository still need that repository's normal build and behavior checks before release.
